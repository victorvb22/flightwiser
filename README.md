# Flightwiser

ML search-and-diagnostic tool for individual flights, built on real ADS-B data (OpenSky Network): real trajectory, trajectory anomaly score, deviation vs. a simulated optimal profile (OpenAP), and route directness (great-circle distance vs. distance actually flown). v1: no fuel/mission-based anomaly categorization, no bonus KPI.

## Structure

```
backend/    REST API (FastAPI), data clients, ML models, preprocessing scripts
frontend/   SPA (React + TypeScript, Vite)
data/       data/raw/ (raw historical dataset, not versioned) — data/reference/ and data/processed/ regenerated by the scripts
```

## Historical dataset preprocessing

```
cd backend
python scripts/preprocess_historical.py
```

Reads `data/raw/flights_raw.csv`, produces `data/processed/flights_clean.parquet` (point deduplication, filtering of ADS-B artifacts — outlier position/altitude/vertical speed —, speed recomputation, destination airport inference, aircraft type enrichment).

## Aircraft categorization

Before any score is computed, every flight is classified by typecode through a lookup table (`data/reference/aircraft_categories.csv`, typecode -> category, generated by `scripts/build_aircraft_categories.py`) rather than "OpenAP recognizes this typecode," as an earlier version did: OpenAP only covers around forty typecodes for its own simulation needs, which let real airliners it doesn't model yet (A330-900, A220, CRJ-1000, 787-10...) fall into `petit_avion` by default — found directly on the training dataset, not a hypothesis. The table is built in layers: helicopter detected automatically via the `icaoaircrafttype` field of `aircraft_database.csv`, aggregated by typecode (reliable, verified by hand), avion_ligne/jet_affaire automatic for typecodes OpenAP recognizes (except `c550`/`glf6`, the only two business jets on its list), everything else classified by hand for the typecodes actually encountered in the dataset. A typecode absent from the table returns `None` ("unidentified") — no score is computed rather than a guessed default classification.

- `avion_ligne` / `jet_affaire` / `petit_avion` (`services/aircraft_category.categorize`): a single shared distribution would systematically penalize whichever group is a minority, their speed/altitude/climb-rate distributions being too different (a business jet cruises noticeably faster and higher than a touring aircraft).
- `helicoptere`: structurally outside a fixed-wing distribution even for a normal flight (hover, no classic climb/cruise/descent phases).

Both the anomaly model and the route-directness model train on all four categories — checked directly on real data before extending directness to all four, not assumed: median/mean route-directness ratio differs meaningfully between `jet_affaire` (0.895/0.839) and `petit_avion` (0.851/0.761), so pooling them would have diluted `petit_avion`'s own baseline. Only the deviation model doesn't split this way: it has no OpenAP performance model for any of the three non-airliner categories, so there's no distribution to split in the first place (`categorize`, not a separate two-way variant).

Training (below) is restricted to aircraft that passed through Europe on 2022-06-27; a random flight draw, on the other hand, is worldwide. A helicopter flight whose trajectory never touches Europe gets an `out_of_training_scope` flag on its anomaly score (mission profile varies too much by region to trust the baseline outside the training zone) — checked for `avion_ligne`/`petit_avion` that this wasn't necessary (`scripts/check_geographic_consistency.py`).

## Trajectory anomaly model

```
cd backend
python scripts/extract_historical_for_training.py --date 2022-06-27   # once, ~20-45 min depending on the bbox
python scripts/train_anomalie.py
```

Fits a diagonal Gaussian per category (avion_ligne / jet_affaire / petit_avion / helicoptere) on 7 summary flight features (brief section 11), on landed flights from two merged and deduplicated sources (`scripts/_training_data.py`) — `data/processed/flights_clean.parquet` and `data/processed/flights_historical_features.parquet` (Europe extraction below) — and writes the parameters to `models/artifacts/anomalie_params.json`, used by `models/anomalie.py` at scoring time.

### Anomaly type (`models/anomaly_type.py`)

For an `avion_ligne` flight whose score above flags an anomaly, a second, entirely independent model attempts to name which of three known signatures it matches: `go_around`, `holding`, or `emergency_descent`. This is a separate classical ML project ([github.com/victorvb22/flight-trajectory-detection](https://github.com/victorvb22/flight-trajectory-detection)) — a Random Forest trained on **synthetically** injected anomalies (never a real one), reconstructed identically inside flightwiser:

```
cd backend
python scripts/train_anomaly_type_classifier.py
```

Replays the source notebook exactly (same columns, split, hyperparameter grid, random seeds — the original model was never persisted, the only way to get it back), from `data/processed/anomaly_type_dataset.csv` (copied from the source project), and writes `models/artifacts/anomaly_type_classifier.joblib`. Verified: the reproduced metrics (F1 per class) match those published in the source project's README. `models/anomaly_type.py` ports the notebook's 6 features to flightwiser's internal format (`vitesse_verticale` already smoothed by `services/trajectory_cleaning.py` — no need to reimplement the notebook's own smoothing).

`pipeline.py` computes this type whenever applicable (not only when the score flags an anomaly) — it's up to the frontend to decide when to show it, rather than duplicating a threshold here that only exists on the UI side. A `normal` result on a flight otherwise flagged as anomalous isn't a model failure: it means none of the three known signatures match, which is honest information in its own right.

## Trajectory deviation model

`models/ecart_trajectoire.py` compares a flight's real trajectory to a profile simulated by [OpenAP](https://openap.dev) for the same aircraft type, phase by phase (climb/cruise/descent). No training or artifact — OpenAP is called on demand, from `compute(trajectoire, typecode)`. A typecode OpenAP doesn't recognize (`jet_affaire`/`petit_avion`, helicopters included) returns `None` rather than a score computed against a silently substituted A320 performance model — no fallback simulation.

## Route directness model

`models/directness.py` computes the ratio of great-circle distance to distance actually flown between the trajectory's first and last point — a ratio close to 1 signals a direct route, a lower one suggests a holding pattern, a diversion, or extended ATC vectoring. The only one of the three that looks at the trajectory's shape rather than its speed/altitude values. Training (empirical percentiles, no Gaussian):

```
cd backend
python scripts/train_directness.py
```

## Free search (`GET /api/v1/flights/{identifiant}`) and random flight (`GET /api/v1/flights/random/search`)

OpenSky blocks requests coming from Render/Railway/Cloudflare Workers at the network level (see the Limitations section below): the deployed backend no longer calls it live at all. `pipeline.py` looks up the identifier (registration, callsign, or icao24) in a pool of pre-fetched real flights (`services/flight_pool.py`, `data/reference/flight_pool.jsonl`, bundled with the deployment), checks `flights_cache` (Supabase) under the `{icao24}_{UTC date}` key, and if absent writes the pool's result to the cache (`source: "vedette"`) then marks the flight as served (`pool_served`, Supabase — persists across a redeploy, whose disk is ephemeral) so a future random draw never serves it again. A search already seen the same day therefore triggers no extra write at all (`source: "cache"` vs. `"vedette"`).

### Flight pool (`services/flight_pool.py`)

Fed offline, not on demand:

```
cd backend
python scripts/collect_opensky_pool.py   # from a machine where OpenSky is actually reachable — not a cloud host
python scripts/build_flight_pool.py      # regenerates data/reference/flight_pool.jsonl from the collected file
```

`collect_opensky_pool.py` runs continuously (manual stop, Ctrl+C, flushes every 10 lines) and directly reuses the internal functions of `services/opensky_live.py` — the same code path a live call would have taken — so each collected flight is exactly in the shape a real API response would be. Written outside the repo (`D:/ML_data/flightwiser/opensky_fetch/pool.jsonl` by default), deliberately without going through `flights_cache` so as not to pollute the search history with speculative draws.

### Supabase setup

Paste `backend/db/schema.sql` once into the Supabase dashboard's SQL Editor (creates `flights_cache` and `pool_served`), then fill in `SUPABASE_URL`/`SUPABASE_KEY` (secret key, Project Settings > API) in `backend/.env`. Accessed via direct REST (PostgREST) through `services/cache.py`/`services/pool_tracking.py`, no SDK — both of these writes are best-effort: any network/HTTP error is logged and treated as a miss/no-op rather than failing a search.

## Historical training data (`scripts/extract_historical_for_training.py`)

```
cd backend
python scripts/extract_historical_for_training.py --date 2022-06-27
```

OpenSky doesn't publish a public Trino instance, but a public bucket (`s3.opensky-network.org/data-samples`) holds a full worldwide state-vector extraction every Tuesday evening (for the previous day), from 2017-06-05 to 2022-06-27. The script downloads the 24 hourly files (cached under `D:/ML_data/flightwiser`, or `IMPORT_DATA_DIR` if set — never in the repo), locates, in two local passes (`services/opensky_historical.py`), the aircraft that passed through a wide Europe bbox that day (a flight taking off there can land anywhere in the world, so a single-pass geographic filter would truncate the trajectory), reconstructs and cleans each flight (`services/trajectory_cleaning.py`, shared with the rest of the project), and writes `data/processed/flights_historical_features.parquet` — used, deduplicated against `flights_clean.parquet` (`scripts/_training_data.py`), by `scripts/train_anomalie.py` and `scripts/train_directness.py`.

The bbox only decides which aircraft become candidates; once an aircraft qualifies, its full trajectory is extracted wherever it actually went — widening the bbox therefore introduces no truncation, only more diversity.

### Visualisations

`components/visualisations/` has real chart rendering (brief section 7), built with the dataviz skill's method — CVD-safe validated palette, a chosen light/dark mode (not a plain flip), color roles consistent with their job (sequential for altitude, status for severity, a single color for a single-series histogram — never one for the other):

- **VueTrajectoire**: SVG trajectory plot (equirectangular projection), colored by altitude (sequential blue ramp), ramp legend, crosshair + tooltip on hover or keyboard navigation (←/→), collapsible data table (`<details>`) so every value stays accessible without hovering.
- **JaugeEcart**: one meter per phase (climb/cruise/descent) + overall deviation, severity color from the status palette (never a series color), text detail always visible under the bar.
- **ScoreAnomalie**: stat tile (percentile rank + severity badge), contributing features as tags, `out_of_training_scope` warning for a helicopter outside the training zone, anomaly-type tag (go-around/holding/emergency descent) for a flagged airliner.
- **DirectnessGauge**: same visual language as ScoreAnomalie for the directness score.
- **HistogrammeScores**: 10-bin bar chart, used for the Aggregate view's score distributions.

## Aggregate view (`GET /api/v1/flights/history`)

Reads `flights_cache` (Supabase, `services/cache.get_all_cached_flights`) — every flight ever searched through the app, not a separate batch import. Resolves each icao24 to a registration when known (`services/aircraft_database.get_registration`, otherwise the raw icao24), a typecode, and a category (same categorization as the anomaly model); table sortable on every column, score histograms and stats computed on the frontend (`pages/VueAgregee.tsx`) from that same list.

## Limitations

The original design resolved an identifier to an icao24 and fetched its trajectory live from OpenSky on every search — no pool, no pre-fetching. It worked locally, but OpenSky blocks requests coming from the shared, dynamic IP ranges of small cloud hosts at the network level (an anti-abuse measure OpenSky documents) — verified directly on Render, Railway, and a Cloudflare Worker relay (all blocked), while the exact same calls succeed without issue from GitHub Actions (a larger host, with a better-established anti-abuse reputation, that OpenSky doesn't block).

Rather than keep working around a block outside this project's control, live search was replaced with a pool of real flights collected ahead of time from a reachable machine, reusing the same code path a live search would have taken (`services/opensky_live.py`, cf. the Free search section above) — every flight in the pool is therefore identical in shape and content to what a live call would have returned, just recorded in advance instead of on demand.

## Deployment

Frontend (Vercel) and backend (Render) hosted separately — Vercel isn't a good fit for the backend: heavy dependencies (pandas/numpy/pyarrow/openap/scipy) and an ~94 MB aircraft database kept in memory, which a cold serverless start would reload on every request.

**Backend (Render)**: `render.yaml` at the repo root describes the service (`New` > `Blueprint` on the Render dashboard rather than manual configuration). Secrets to fill in on the dashboard (never in the repo): `SUPABASE_URL`, `SUPABASE_KEY`, `CORS_ALLOWED_ORIGINS` (the Vercel domain, once known). No OpenSky secret here: the deployed backend doesn't call it at all anymore (see the Limitations section) — `OPENSKY_CLIENT_ID`/`OPENSKY_CLIENT_SECRET` are only used locally, by `scripts/collect_opensky_pool.py` (`backend/.env`).

**History — OpenSky relay (`cloudflare-relay/worker.js`)**: before the pool existed, an attempt to work around Render's network block toward `opensky-network.org` (a full connection timeout, confirmed on two different hosts) went through a Cloudflare Worker relaying only calls to `opensky-network.org`/`auth.opensky-network.org`. Also blocked (the same shared IP ranges, cf. Limitations) — the code is kept (`services/opensky_client.py` still supports `OPENSKY_RELAY_URL`/`OPENSKY_RELAY_SECRET` if they're set) but no longer used by the current deployment.

**Frontend (Vercel)**: Root Directory = `frontend` (monorepo). `frontend/vercel.json` adds the necessary SPA rewrite (`BrowserRouter`: without it, a direct link or a refresh on `/agregee` or `/documentation` returns a 404 on static hosting). Environment variable `VITE_API_BASE_URL` = the Render backend's URL.

Bootstrap order (cross-dependency): deploy the backend first, grab its URL, put it in `VITE_API_BASE_URL` on the Vercel side, deploy the frontend, grab its URL, then update `CORS_ALLOWED_ORIGINS` on the Render side and redeploy.
